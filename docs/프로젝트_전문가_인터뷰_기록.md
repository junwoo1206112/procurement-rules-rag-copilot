# Procurement Rules RAG Copilot — 전문가 인터뷰 기록

## 프로젝트 브리프

- 프로젝트명: Procurement Rules RAG Copilot
- 한 줄 목표: 조달청 행정규칙에서 검증 가능한 근거를 찾아 인용형 답변을 제공한다.
- 사용자: 조달 규정을 확인하는 실무자와 RAG·LLM 직무 채용 담당자
- 입력 데이터: 국가법령정보센터의 조달청 행정규칙, 저작권법 제7조 이용 근거, 로컬 `LAW_API_OC`
- 산출물: 원문 링크·조항·근거 청크가 포함된 답변과 평가 리포트
- 제외: 법률 판단, 자동 입찰서 작성, 권한 관리, 구형 HWP 완전 지원

## 교차 검증

**전문가 A:** 화면 HTML 수집은 30건 모두 3개 블록만 생성해 실제 조문 RAG 근거가 되지 못한다. 공식 JSON 본문 API로 전환해야 한다.

**전문가 B:** 메타데이터 목록만으로는 채용 담당자가 실제 RAG 품질을 검증할 수 없다. 실제 조문 단위 색인, 고정 평가 세트, 비교 리포트가 필요하다.

**결정:** 승인된 `LAW_API_OC`를 로컬 `.env`에서만 읽고, 공식 행정규칙 JSON 본문을 수집·구조화한 뒤 평가를 진행한다.

## 초기 고위험 가정 (해결 이력)

- 행정규칙 JSON 본문 API의 정확한 응답 구조와 호출 파라미터는 승인된 OC로 실제 검증해야 한다.
- CPU 환경에서는 여러 후보를 한꺼번에 주면 로컬 모델이 빈 claim을 반환할 수 있다. 이 경우 검증된 원문 발췌로 보류하며, 생성 응답은 최소 관련성·인용 검증을 통과할 때만 반환한다.

## 실행시간 교차 검증

**전문가 A:** 30건 순차 API 호출은 실행 환경의 약 60초 제한을 넘는다. 5건 배치와 즉시 체크포인트가 필요하다.

**전문가 B:** 중간 실패로 평가 데이터가 바뀌면 성능 주장도 바뀐다. 각 배치의 성공·실패·해시를 누적 기록하고 재시작 시 성공 문서를 건너뛰어야 한다.

**결정:** `collect_corpus`는 `--offset`, `--limit` 배치를 지원하고 `collection-report.json`에 누적 기록한다. 전체 30건 완료 전에는 평가 수치를 주장하지 않는다.

## P0 해결 교차 검증

**전문가 A:** 수집 파일과 FastAPI의 인메모리 저장소가 분리되어 있으면 새 환경에서 빈 인덱스가 된다. 검증된 `collected-chunks.json`만 서버 시작 시 로드하고, 수동 수집 API도 동일한 공식 JSON 경로를 사용해야 한다.

**전문가 B:** 법령은 페이지 번호보다 조항이 검증 위치다. API 본문에서 `제n조` 라벨을 청크 섹션으로 보존하고, README가 페이지 인용을 약속하지 않도록 고쳐야 한다.

**결정·검증:** 서비스 시작 시 30개 문서·2,187개 청크를 자동 색인했고, 2,161개 청크에 조항 섹션을 보존했다. `pytest` 23개를 통과했다. 평가 증거(P0)는 다음 단계에서 고정 질의셋과 비교 리포트로 해결한다.

## P0 평가 증거 교차 검증

**전문가 A:** 평가 정답은 긴 조항이 여러 청크로 분할되는 경우를 모두 허용해야 한다. 한 조항의 첫 청크만 정답으로 두면 올바른 조항의 다른 청크를 오답으로 만든다.

**전문가 B:** 실제 임베딩이 없는 상태에서 `Dense`라는 표현을 쓰면 안 된다. 구성명과 한계를 리포트에 명시하고, 재정렬이 항상 개선된다고 주장하지 않아야 한다.

**결정·검증:** 30개 조항 조회와 3개 답변 불가 질의를 고정했다. 동일 코퍼스에서 Hybrid는 TF-cosine보다 Recall@5가 0.5667→0.7000으로 개선됐고, 현재 휴리스틱 재정렬은 0.6333으로 더 낮았다. 따라서 재정렬은 개선 과제로 공개하며, `docs/evaluation-report.md`에 측정 조건과 한계를 기록했다. 다만 이는 법령 조항 검색의 예비 회귀평가이며, 명세가 요구한 자격·일정·제출물·평가기준·비교 유형을 검증하려면 공개 RFP/입찰 공고 코퍼스 추가가 필요하다.

## 나라장터 확장 교차 검증

**전문가 A:** 공식 용역 공고 API로 공고번호·기관·일정·기초금액·계약/낙찰 방법을 구조화하면, 일정과 평가 관련 검색을 실제 데이터로 검증할 수 있다. 담당자 연락처는 수집하지 않는다.

**전문가 B:** 공고 API의 이용허락 범위와 개별 RFP 첨부 원문의 이용 조건은 다르다. 첨부자료를 자동 수집해 포트폴리오 코퍼스에 넣으면 개인정보·저작권 검증 결정을 위반할 수 있다.

**결정·검증:** 공식 API로 용역 공고 30건·90청크를 수집했고, 법령과 합친 62문항 평가에서 Hybrid Recall@5는 0.8475, 답변 불가 보류율은 1.0000이었다. RFP 첨부자료는 문서별 공개·이용 조건·개인정보 검사기를 구현한 뒤에만 추가한다. Docker Desktop이 현재 설치되어 있지 않아 Compose E2E는 완료로 처리하지 않는다.

## 평가 범위 교차 검증

**전문가 A:** 공고의 첫 청크만 고르면 공고 개요만 평가되고 일정·가격평가·제출서류 검색이 빠진다. 고정 세트는 질문 유형별로 별도 근거 청크를 선택해야 한다.

**전문가 B:** 평가 코드가 바뀐 뒤 이전 체크포인트를 합치면 숫자는 재현 가능하지 않다. 데이터셋 버전뿐 아니라 측정기 버전, 코퍼스 해시, 실행 환경과 실패 사례를 함께 남겨야 한다.

**결정·검증:** v3 세트는 72문항(답변 가능 69, 답변 불가 3)이며 참가자격·일정·제출서류·평가기준·문서 비교·답변 불가 유형을 모두 포함한다. 필수 유형, 중복 ID, 문서/공고 `split_document_id`, 정답 근거, 문서 비교의 복수 근거를 로더에서 검증한다. `evaluation-report.md`에 코퍼스 SHA-256·Python/OS·실패 사례와 함께 TF-cosine, Hybrid, Hybrid+rerank를 기록했다. 현 v3에서 Recall@5는 각각 0.5362/0.5362/0.3333으로, Hybrid 우위를 주장하지 않으며 reranker는 기본 경로에서 제외한다. 실제 임베딩(Dense) 전체 측정은 별도 안정화 과제로 남긴다.

## 기본 검색 회귀 검증

**전문가 A:** 공고번호 필터 안에서 평가표의 제목 단어가 질문 본문보다 강하면 “제출 서류”에 평가표가 먼저 나올 수 있다.

**전문가 B:** 재정렬 모드로만 테스트를 통과시키면 기본 사용자 경로의 오류를 숨긴다. 기본 Hybrid가 질문의 본문 근거를 우선하는지 확인해야 한다.

**결정·검증:** Hybrid 점수에 본문 어휘 일치도를 분리해 반영했고, 공고번호 `2026-001`의 제출 서류 질의가 기본 모드에서 제출 청크를 최상위로 반환하도록 회귀 테스트를 변경했다. 전체 테스트는 28개 통과했다.

## 실제 임베딩·Hybrid 교차 검증

**전문가 A:** 테스트 코퍼스의 임베딩 캐시가 실제 코퍼스 캐시를 덮어쓰면 첫 실행마다 2,289개 청크를 다시 벡터화한다. 캐시 키는 코퍼스와 임베딩 설정에 종속돼야 한다.

**전문가 B:** Dense 점수만 양수여도 무관한 질문이 통과할 수 있다. 실제 문서 어휘 일치(BM25)가 없는 경우 답변을 보류해야 하며, Dense+BM25 결합이 Dense 단독보다 낮으면 그 사실을 숨기면 안 된다.

**결정·검증:** 캐시 파일명을 코퍼스·설정 해시로 분리하고, 600자 입력·256 토큰 제한을 적용했다. 답변과 평가는 상위 근거의 BM25 양수 일치를 최소 게이트로 사용해 답변 불가 보류율 1.0000을 유지했다. v3.7 72문항에서 Dense/TF-cosine/Hybrid/Hybrid+rerank Recall@5는 0.7536/0.5362/0.7391/0.6377이었다. Hybrid는 TF 기준선보다 높지만 Dense 단독보다 낮으므로 가중치 튜닝 과제로 남긴다. 임베딩 지연시간은 배치 평가의 질문당 평균이므로 단건 p50/p95를 별도로 측정할 때까지 평가 종료 게이트는 열어 둔다.

## 운영 재현성 확인

**전문가 A:** Compose 파일이 있어도 Docker 명령이 없는 환경에서는 새 환경 재현을 증명할 수 없다.

**전문가 B:** 설치되지 않은 도구를 완료처럼 표시하면 포트폴리오 신뢰도가 떨어진다. 실행 불가 조건과 재실행 명령을 분리해 기록해야 한다.

**결정·검증:** Docker Desktop(Engine 29.7.2)에서 Compose를 실제 실행했다. CPU 전용 PyTorch를 먼저 설치하도록 Dockerfile을 보완해 CUDA 의존성 다운로드를 제거했고, 검증된 법령·나라장터 코퍼스만 이미지에 포함했다. `/health`는 67개 문서·2,289개 청크 자동 색인을 반환했다. `qwen2.5:3b` 모델을 내려받은 뒤, 조달등록팀 운영규정 제1조 질문에서 `grounded` 상태·모델명·원문 인용을 확인했다. 검색 근거가 혼합되어 claim 검증이 실패하는 경우에는 `grounded_demo` 원문 발췌로 안전하게 보류됨도 확인했다.

## 단건 성능 교차 검증

**전문가 A:** 배치 처리의 질문당 평균을 p50/p95라고 쓰면 실제 사용자 응답 시간을 과장할 수 있다.

**전문가 B:** Dense, Hybrid, reranker는 같은 질의·같은 코퍼스에서 단건 검색으로 비교해야 CPU 데모의 지연시간을 설명할 수 있다.

**결정·검증:** v3.8에서 72문항을 단건 검색으로 다시 측정했다. Recall@5는 Dense/TF-cosine/Hybrid/Hybrid+rerank가 0.7536/0.5362/0.7391/0.6377이고, Hybrid p50/p95는 108.266/706.824ms, Dense는 251.156/334.155ms다. 네 구성 모두 답변 불가 보류율은 1.0000이다. Hybrid는 기준선보다 품질이 높지만 Dense 단독보다 낮으며, reranker도 품질을 낮추므로 CPU 데모 기본값은 `lexical_hybrid`로 유지한다.

## 품질 고도화 교차 검증

**전문가 A:** 검색 상위 결과 전체를 생성 모델에 전달하면 직접 조항 근거와 주변 청크가 섞여 빈 claim이 발생할 수 있다. 검색 순위를 바꾸지 않고, 답변 단계에서 문서명·조항·공고번호·본문 어휘가 직접 일치하는 근거를 선택해야 원인을 분리할 수 있다.

**전문가 B:** `grounded` 비율만 높이면 근거 없는 문장을 통과시키는 지표 게임이 된다. 검색 Recall@5, 생성용 선택 근거 Recall, citation P/R, `grounded`·`grounded_demo`·`insufficient_evidence` 상태를 분리하고, 실제 LLM 생성과 결정론적 인용 계약을 혼동하지 않아야 한다.

**결정:** 일반 질문에는 직접 관련 청크 하나를 우선 전달하고, `비교`·`차이`·`각각` 질문에는 문서별 근거를 보존한다. 관련 근거가 없으면 모델을 호출하지 않으며, claim 검증 실패 시 검증된 원문 발췌만 반환한다. 상태명은 API 호환성을 위해 유지하고 로그·평가에서만 제한된 원인 코드를 기록한다.

**측정·검증:** v4.0 고정 72문항·코퍼스 SHA-256 `35540f23…e5f7509e` 단건 평가에서 검색 Recall@5는 lexical_hybrid/TF-cosine/hybrid/hybrid_rerank/embedding 순으로 0.5362/0.5362/0.7391/0.6377/0.7536이었다. 생성용 선택 근거 Recall은 0.2319/0.2029/0.2754/0.2319/0.3043으로 별도 기록했다. 모든 구성에서 답변 불가 3문항은 `insufficient_evidence`로 보류됐다. 세부 수치·실패 사례는 `docs/evaluation-report.md`와 `data/evaluation-results.json`에 있다.

**한계:** `deterministic_evidence_contract`의 `grounded`는 실제 Ollama 문장 품질이 아니라 선택 근거와 인용 가능성을 검증한 상태다. 실제 모델 평가는 CPU·모델 준비 상태에 따라 달라지며 대표 E2E 질의로 별도 기록한다. 임베딩의 최초 모델 로드·코퍼스 벡터화 비용은 단건 p50/p95에서 제외하므로, 더 높은 Recall만으로 Docker CPU 기본 경로를 바꾸지 않는다.

## 마감 교차 검증 (2026-08-24)

**전문가 A:** 수집·색인·검색·답변 안전장치·평가·컨테이너가 하나의 실제 실행 경로로 이어지는지 다시 확인해야 한다. 특히 템플릿·합성 fixture만 통과한 결과를 실코퍼스 결과처럼 쓰면 안 된다.

**전문가 B:** 포트폴리오는 최고 성능 수치보다 재현 가능성과 한계의 정직한 공개가 중요하다. 테스트 명령과 README의 수치가 현재 평가 리포트와 일치하는지, 불필요한 산출물이 Git에 섞이지 않는지도 확인해야 한다.

**검증 결과:** 당시 표준 임시 폴더를 사용하는 `python -m pytest -q -p no:cacheprovider`가 37개 테스트를 통과했다. 이후 실제 LLM 평가 고도화 뒤 최신 전체 테스트는 44개를 통과했다. OpenSpec 현행 명세 2개는 strict 검증을 통과했다. Docker Compose의 API·Ollama 컨테이너가 실행 중이며 `/health`는 67개 문서·2,289개 청크를 반환했다. v4.0 수치와 한계는 `evaluation-report.md` 및 README·포트폴리오 케이스 스터디가 일치하게 기록한다.

**조치:** 프로젝트 루트에 남을 수 있는 `.pytest-*` 임시 폴더를 Git 제외 대상으로 추가하고, Windows 권한에 의존하는 `--basetemp .pytest-tmp` 예시는 README에서 제거했다.

**최종 판정:** P0·P1 기능 결함은 재현되지 않았으며, 남은 항목은 실제 LLM 생성 품질의 대규모 평가와 검색 성능 튜닝이라는 선택적 고도화다. 현재 목표인 근거 중심 RAG 포트폴리오의 구현·검증·문서화 종료 게이트를 충족한다.

## 실제 LLM 생성 평가 고도화 기록

**전문가 A:** 선택 근거와 citation ID가 맞더라도 생성문 자체가 근거를 정확히 요약했는지는 별도 증거가 필요하다. 다만 두 번째 LLM으로 법률 문장을 자동 채점하면 새로운 환각과 비용이 생긴다.

**전문가 B:** 모델 연결 실패를 낮은 답변 품질처럼 집계하면 수치가 왜곡된다. 결정론적 근거 계약과 실제 생성 평가를 분리하고, 모델·프롬프트·코퍼스 식별자와 지표 분모를 공개해야 한다.

**결정:** 실제 Ollama 평가는 별도 JSON·Markdown 산출물로 저장한다. 반환 인용과 고정 정답 근거의 일치, 답변 불가 보류, 실행 실패를 자동 집계하되 생성문 의미·법률 해석의 최종 평가는 우선 검토 사례를 사람이 확인하는 범위로 제한한다.

**대표 실행 결과:** Docker Compose의 `qwen2.5:3b`, `lexical_hybrid`, v3 코퍼스에서 조항·참가자격·공고 정보·일정·평가기준·제출서류·문서 비교·답변 불가 8문항을 실제 실행했다. 인프라 실패는 0건, 답변 가능 7문항의 인용 정답 근거 일치는 3건(0.4286), 답변 불가 1문항의 안전 보류는 1건(1.0000)이었다. `grounded_demo`는 4건으로, 모델 JSON/claim 검증 실패 시 검증된 원문 발췌로 전환됨을 확인했다.

**전문가 A:** 일정·계약/평가·제출서류 질의에서 개요 청크가 인용된 사례는 생성 모델만의 문제가 아니라 `lexical_hybrid` 기본 경로의 특정 항목 검색 한계를 드러낸다. 인용 불일치를 성공으로 집계하지 않고 검토 대상으로 남긴 것은 맞지만, 검색 개선 전에는 이 수치를 답변 품질로 홍보해서는 안 된다.

**전문가 B:** 답변 불가 보류와 인프라 실패 분리는 의도대로 작동했다. 다만 8문항은 대표 실행일 뿐 전체 72문항의 생성 품질을 뜻하지 않는다. `grounded_demo` 비율도 모델의 JSON 준수·claim 검증 실패를 나타낼 뿐 법률 정확도 지표가 아니다.

**종료 판정:** 실제 생성 평가 파이프라인의 안전성·재현성 종료 게이트는 충족했다. 다음 선택적 개선은 별도 변경으로 분리한다: (1) 일정·제출서류·평가기준에 대한 도메인 질의 확장 또는 재순위화, (2) 모델의 구조화 출력 준수율을 높이기 위한 재시도·출력 제약 실험. 현재 결과는 `live-llm-evaluation-report.md`에 그대로 공개한다.
