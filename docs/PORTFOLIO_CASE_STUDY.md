# Procurement Rules RAG Copilot | 포트폴리오 케이스 스터디

## 한 줄 소개

조달 관련 행정규칙을 대상으로, 답변보다 **검증 가능한 조항 근거**를 우선하는 로컬 RAG Copilot을 설계·구현·평가했습니다.

## 해결하려 한 문제

입찰·계약 규정은 문서가 길고 조건이 많아 검색 결과만으로는 확인이 어렵습니다. 일반적인 RAG는 관련 없는 상위 문서를 인용하거나 근거가 부족한 내용을 자연스럽게 만들어낼 수 있습니다. 이 프로젝트는 답변마다 문서명·조항·원문 URL을 연결하고, 그 연결이 불가능하면 답변을 보류하도록 만들었습니다.

## 내가 구현한 내용

- 국가법령정보센터 원문 수집 과정에서 허용 도메인, 문서 제목, 원문 SHA-256을 검증했습니다.
- 문서 제목·문서 유형·발행일 메타데이터를 가진 조항 단위 청크를 자동 색인했습니다.
- `lexical_hybrid`(TF-cosine+BM25)를 즉시 재현 가능한 CPU 기본 경로로 두고, 임베딩+BM25 `hybrid`와 Dense를 같은 평가 세트에서 비교했습니다.
- 답변 전용 근거 선택기를 두어 일반 질의는 직접 관련된 한 건을, 비교 질의는 문서별 근거를 유지하도록 구현했습니다.
- 인용 검증 실패나 모델 오류 시 모델 문장을 신뢰하지 않고 검증된 원문 발췌로 제한했습니다.
- Docker Compose로 API와 로컬 Ollama를 함께 실행해 새 환경의 빈 인덱스 문제를 방지했습니다.

## 검증 결과

| 항목 | 결과 |
| --- | --- |
| 실제 색인 | 공식 원문 67개 문서, 2,289개 청크 |
| 고정 평가 | 72문항, 검색·인용·선택 근거·지연시간 동시 측정 |
| 검색 Recall@5 | `lexical_hybrid` 0.5362 / `hybrid` 0.7391 / Dense 0.7536 |
| 자동 테스트 | 44개 통과 |
| Docker E2E | 자동 색인, 로컬 Ollama 생성·인용 평가, 근거 부족 보류 확인 |

전체 지표와 측정 조건은 `evaluation-report.md`에 재현 가능하게 기록했습니다. 임베딩 모델의 최초 로드와 코퍼스 벡터화 비용은 단건 p50/p95에 포함하지 않았으므로, 이를 숨기고 `hybrid`를 기본 경로로 바꾸지 않았습니다.

실제 Ollama(`qwen2.5:3b`) 대표 8문항 평가에서는 답변 가능 7문항 중 인용 정답 근거 일치가 3건(0.4286)이었고, 답변 불가 1문항은 안전하게 보류했습니다. `grounded_demo`가 4건 발생했으며, 이는 JSON/claim 검증 실패 시 답변을 꾸며내지 않고 원문 발췌로 전환한 결과입니다. 이 표본은 전체 생성 품질을 뜻하지 않으며, 낮은 인용 일치를 개선된 성능으로 주장하지 않습니다.

## 문제를 발견하고 고친 사례

실제 Docker E2E에서 `조달등록팀 운영규정`을 묻는 질의에, 제목의 일반 단어가 겹친 다른 조달청 문서가 인용되는 문제를 발견했습니다. 답변 형식은 근거 기반이었지만 **가장 직접적인 근거가 아니었습니다**. 제목 매칭을 일반 단어 포함 여부가 아니라 의미 있는 질문·문서 제목 토큰의 교집합으로 좁히고, 회귀 테스트를 추가했습니다. 이 사례는 ‘인용이 있다’와 ‘올바른 인용이다’를 구분한 검증 경험입니다.

## 안전성·한계

- 법률·계약·입찰의 최종 판단을 대신하지 않으며, 원문과 최신 공고를 다시 확인해야 합니다.
- `deterministic_evidence_contract` 평가는 근거·인용 계약 충족 여부이지, LLM 생성 문장의 사실성 평가 자체는 아닙니다.
- 일반 단어만 겹치는 질의는 근거 부족으로 보류될 수 있습니다. 이는 답을 꾸며내는 것보다 안전하지만, 향후 질의 확장·재순위화 개선 대상으로 남겼습니다.
- 실제 생성 평가는 일정·평가기준·제출서류에서 공고 개요가 인용되는 사례를 발견했습니다. 인용 불일치가 자동 검토에서 성공으로 집계되지 않도록 했지만, 검색 고도화 전에는 높은 생성 품질을 주장하지 않습니다.

## 60초 발표 흐름

1. “공공 조달 규정은 답변의 유창함보다 조항 근거가 중요하다고 보고, 근거 우선 RAG를 만들었습니다.”
2. “수집부터 출처·해시를 검증하고 67개 문서, 2,289개 청크를 자동 색인했습니다.”
3. “72문항 검색 평가와 8문항 실제 생성 평가를 분리해, 높은 검색 점수와 실제 생성 품질을 혼동하지 않았습니다.”
4. “Docker 실환경에서 잘못된 직접 근거와 JSON 검증 실패를 발견해, 성공으로 집계하지 않고 회귀 테스트와 검토 리포트로 고정했습니다.”
5. “그래서 잘 모르는 경우나 검증 실패 시 답을 꾸며내지 않는 시스템을 구현했습니다.”

## 면접 예상 질문

**왜 최고 Recall을 낸 Dense를 기본값으로 두지 않았나요?**  
CPU 환경에서 외부 모델 다운로드 없이 즉시 재현되는 경로를 데모 기본으로 삼았기 때문입니다. Dense와 hybrid의 더 높은 Recall은 명확히 기록했지만, 모델 준비 비용이 제외된 수치만으로 운영 기본값을 바꾸면 재현성과 설명 가능성이 떨어집니다.

**인용이 있다고 답변이 안전한가요?**  
아닙니다. E2E에서 실제로 형식상 인용은 있었지만 직접 근거가 아닌 사례를 발견했습니다. 그래서 답변 생성과 별개로 근거 선택 및 인용 검증을 두고, 그 버그를 회귀 테스트로 고정했습니다.

**다음 개선 계획은 무엇인가요?**  
실제 Ollama 생성 평가는 이미 분리해 기록했습니다. 다음은 일정·제출서류·평가기준에 대한 도메인 질의 확장 또는 재순위화와, 구조화 출력 준수율을 높이는 재시도·출력 제약 실험입니다. 이들은 현재 수치가 충분하지 않다는 사실을 전제로 별도 변경으로 검증합니다.
