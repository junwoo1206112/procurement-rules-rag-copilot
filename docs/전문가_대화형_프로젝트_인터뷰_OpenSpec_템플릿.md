# 전문가 대화형 프로젝트 인터뷰 · OpenSpec 템플릿

목적: 모호한 아이디어를 두 명의 독립 전문가가 검증하고, 사용자가 확인한 결정을 OpenSpec 산출물로 전환하는 재사용 가능한 진행 템플릿입니다. 인터뷰는 결정을 대신하지 않으며, 제품 범위·데이터·성공 기준처럼 사람의 판단이 필요한 항목은 반드시 사용자에게 확인합니다.

## 1. 사용 방법

1. 아래의 `프로젝트 브리프`를 채운다.
2. 전문가 A와 B가 서로의 가정을 질문·반박·수정한다.
3. 사용자 확인이 필요한 결정만 따로 모아 승인받는다.
4. 결정 원장을 OpenSpec `proposal.md`, `design.md`, `specs/`, `tasks.md`에 반영한다.
5. 구현 후 평가 결과와 한계를 README 및 포트폴리오에 공개한다.

## 2. 프로젝트 브리프

```md
- 프로젝트명: <이름>
- 한 줄 목표: <누구의 어떤 문제를 어떻게 해결하는가>
- 사용자: <주 사용자와 사용 맥락>
- 핵심 입력/데이터: <출처·권한·형식>
- 핵심 산출물: <사용자가 받는 결과>
- 지원 직무와의 연결: <공고의 어떤 요구사항을 증명하는가>
- 시간/비용 제약: <예: 2주, 무료·로컬 우선>
- 명시적 제외 범위: <하지 않을 것>
```

## 3. 역할 정의

| 역할 | 관점 | 반드시 검증할 질문 |
| --- | --- | --- |
| 전문가 A — 기술 아키텍트 | 구현 가능성, 데이터 흐름, 보안, 재현성 | “입력에서 결과까지 무엇이 사실로 검증되는가?” |
| 전문가 B — 제품·포트폴리오 심사자 | 직무 적합성, 사용자 가치, 차별성, 증거 | “채용 담당자가 3분 안에 실력을 확인할 수 있는가?” |
| 사용자 — 의사결정자 | 목적, 우선순위, 허용 범위 | “이 선택이 내가 원하는 결과와 제약에 맞는가?” |

## 4. 인터뷰 진행 규칙

- 전문가 A가 제안하면 전문가 B는 사용자 가치·검증 가능성 관점에서 반문한다.
- 전문가 B가 요구하면 전문가 A는 구현 범위·위험·대안을 답한다.
- 사실과 결정은 구분한다. 현재 저장소/문서에서 확인된 내용은 사실이며, 새 기능의 우선순위는 사용자 결정이다.
- 추정 성능, 허위 데모, 검증하지 않은 수치를 금지한다.
- 각 답변은 `결정`, `근거`, `제약`, `제외 범위`, `검증 방법`을 남긴다.
- 결론 전에는 최소한 범위, 데이터 권리, 성공 지표, 실패 처리, 배포·재현성의 다섯 축을 점검한다.

## 5. 대화 스크립트

### Round 1 — 문제와 직무 적합성

**전문가 B:** 이 프로젝트가 단순 튜토리얼이 아니라는 증거는 무엇이며, 지원 직무의 어떤 요구를 직접 보여주나요?  
**전문가 A:** <핵심 문제, 실제 데이터, 구현 경계, 공고 요구사항의 대응을 답한다.>  
**전문가 B:** 사용자가 결과를 신뢰할 근거와 실패 시 동작은 무엇인가요?  
**결정 기록:** <사용자 확인 필요 여부 포함>

### Round 2 — 데이터와 안전성

**전문가 A:** 데이터의 출처·이용 권한·민감정보 위험은 무엇이며, 수집·갱신·삭제의 경계는 어디인가요?  
**전문가 B:** 이 데이터 크기와 다양성으로 포트폴리오 주장을 뒷받침할 수 있나요? 부족하면 어떤 한계를 공개하나요?  
**결정 기록:** <허용 데이터, 제외 데이터, 계보 메타데이터>

### Round 3 — 시스템 설계와 대안

**전문가 B:** 가장 단순한 구현보다 이 설계를 택한 이유가 무엇인가요?  
**전문가 A:** <선택안·대안·트레이드오프·운영 제약을 답한다.>  
**전문가 B:** 면접에서 이 선택을 수치와 데모로 설명할 수 있나요?  
**결정 기록:** <아키텍처, 재현 방법, 제외한 복잡도>

### Round 4 — 품질·실패·평가

**전문가 A:** 성공과 실패를 각각 어떤 자동화 가능한 지표로 측정하나요?  
**전문가 B:** 지표가 사용자 가치 및 채용 직무와 연결되며, 비교 기준이 공정한가요?  
**결정 기록:** <평가셋, baseline, 지표, 실패 사례 공개 방식>

### Round 5 — 범위 고정과 출시 판단

**전문가 B:** MVP에서 반드시 작동해야 하는 사용 흐름은 무엇이고, 뒤로 미룰 기능은 무엇인가요?  
**전문가 A:** <2주 내 가능한 조각·위험 완화·롤백을 답한다.>  
**사용자 확인:** “이 범위와 제외 범위로 명세 생성을 진행할까요?”

## 7. OpenSpec 전환 규칙

```text
인터뷰 결정 원장
  ├─ Why / 영향 범위                → proposal.md
  ├─ 사용자·시스템의 관찰 가능한 약속 → specs/<capability>/spec.md
  ├─ 기술 선택·대안·위험·롤백       → design.md
  └─ 검증 가능한 작업 순서           → tasks.md
```

- `proposal.md`에는 왜 지금 필요한지, 새 Capability, 영향 범위를 쓴다.
- `spec.md`에는 내부 라이브러리명이 아닌 관찰 가능한 요구사항과 `WHEN/THEN` 시나리오를 쓴다.
- `design.md`에는 선택한 기술과 대안, 위험 완화를 쓴다.
- `tasks.md`에는 각 요구사항을 검증 가능한 작은 작업으로 분해한다.

## 8. RAG 프로젝트 적용 예시 — 공공 조달 문서 RAG

**전문가 B:** 단순 PDF 챗봇과 무엇이 다른가요?  
**전문가 A:** 공개 조달 규정·RFP를 구조 보존으로 파싱하고, 공고번호에 강한 BM25와 의미 검색을 결합한 뒤 재정렬합니다. 답변은 원문 문서·섹션·페이지를 인용하며, 근거가 부족하면 답하지 않습니다.  
**전문가 B:** 문서의 표와 HWP는 신뢰할 수 있나요?  
**전문가 A:** 표는 독립 청크로 보존하고, HWPX를 우선 지원합니다. 구형 HWP는 조용히 변환하지 않고 실패로 표시합니다.  
**전문가 B:** 검색이 좋아졌다는 증거는요?  
**전문가 A:** 동일 질의셋에서 Dense, Hybrid, Hybrid+Reranker의 Recall@k·MRR·nDCG·지연시간을 비교하고, 인용 정합성과 실패 사례를 공개합니다.  
**확정 MVP:** 공개 PDF/HWPX 30~50개, 근거 인용형 Q&A, 로컬 Ollama, Docker Compose, 평가 리포트.  
**제외:** 구형 HWP 완전 지원, 실시간 크롤링, 권한 관리, 자동 입찰서 작성.

## 9. 종료 게이트

다음 항목 모두가 충족될 때만 OpenSpec 명세·구현으로 이동합니다.

- [ ] 사용자가 한 줄 목표와 제외 범위를 승인했다.
- [ ] 데이터 출처와 사용 가능 범위가 확인됐다.
- [ ] 최소 사용자 흐름과 실패 동작이 정의됐다.
- [ ] 최소 한 개의 비교 가능한 품질 지표가 있다.
- [ ] 데모·테스트·재현 방법이 정해졌다.
- [ ] 전문가는 해결하지 않은 고위험 가정을 기록했다.
