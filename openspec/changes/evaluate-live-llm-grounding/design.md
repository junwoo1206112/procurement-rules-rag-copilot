## Context

현재 `run_evaluation`은 검색 결과와 결정론적 근거 선택으로 상태를 계산한다. `--answer-status-mode ollama`은 실제 답변 상태를 호출할 수 있지만, 생성문·모델 실행 실패·정답 근거와의 인용 일치 여부를 질의 단위 산출물로 남기지 않으며, 이 결과를 결정론적 체크포인트와 구분해 관리하지 않는다. 동기는 `proposal.md`와 `프로젝트_전문가_인터뷰_기록.md`의 품질 고도화 교차 검증을 따른다.

## Goals / Non-Goals

**Goals:**

- 고정 72문항에서 실제 Ollama 호출 결과를 결정론적 평가와 별도 파일로 재현 가능하게 저장한다.
- 답변 상태, 선택 근거, 반환 인용, 정답 근거 일치, 모델·프롬프트·코퍼스 식별 정보를 한 질의 결과에 결합한다.
- 모델 연결 실패·시간 초과·형식 오류를 생성 품질과 분리하고, 리포트의 각 분모를 명확히 한다.
- 답변 가능 질의의 인용 일치와 답변 불가 질의의 안전한 보류를 자동 집계하고, 생성문 의미의 사람 검토가 필요한 사례를 식별한다.

**Non-Goals:**

- LLM이 생성한 한국어 문장의 법률 해석 정확도를 자동으로 판정하거나 법률 자문을 제공하지 않는다.
- 사용자 API 응답 스키마, 기본 CPU 검색 구성 또는 Ollama 모델을 변경하지 않는다.
- 외부 평가 LLM·클라우드 API·사용자 대화 로그를 수집하지 않는다.

## Decisions

### 1. 결정론적 평가와 실제 생성 평가를 별도 산출물로 보관한다

`data/evaluation-results.json`은 현재 검색·결정론적 근거 계약의 체크포인트로 유지한다. 실제 생성 실행은 `data/live-llm-evaluation-results.json`에 별도 기록하며, 두 결과의 측정 유형을 같은 파일이나 같은 성공률로 합산하지 않는다.

대안으로 기존 체크포인트에 `ollama` 모드를 덮어쓰는 방식을 검토했다. 이 방식은 모델 미준비 환경에서 재현이 깨지고 `grounded` 비율을 실제 문장 품질처럼 해석하게 하므로 채택하지 않는다.

### 2. 질의별 실행 레코드를 감사 가능한 최소 단위로 고정한다

각 레코드는 `question_id`, 답변 가능 여부·질문 유형, `answer_status`, 생성문, 선택 근거 ID, 반환 citation ID, 정답 근거 ID, 자동 인용 일치 판정, 보류 적절 판정, 실행 결과를 포함한다. 실행 메타데이터에는 모델명, 프롬프트 SHA-256, 코퍼스 SHA-256, 데이터셋 버전, 실행 시각을 기록한다.

생성 프롬프트 원문 전체를 결과에 중복 저장하는 대신 프롬프트 해시를 사용한다. 이렇게 하면 실행 구성을 비교할 수 있으면서 코퍼스 원문과 불필요한 텍스트 복제를 줄인다.

### 3. 자동 판정과 사람 검토 판정을 명확히 분리한다

자동 판정은 반환 citation ID와 고정 평가의 정답 근거 ID가 겹치는지, 답변 불가 질의가 빈 인용의 `insufficient_evidence`인지, 모델 실행이 완료됐는지를 측정한다. 생성문 의미가 실제 근거를 정확히 요약했는지의 최종 판정은 `manual_review_required`로 표시해 사람이 확인할 수 있게 한다.

대안인 ‘두 번째 LLM이 답을 채점’하는 방식은 동일한 환각 위험과 추가 비용을 도입하므로 포트폴리오의 기본 증거로 삼지 않는다.

### 4. 실행 실패는 품질 지표의 분모에서 제외하고 별도 보고한다

`model_unavailable`, `timeout`, `invalid_model_payload` 등 실행 실패는 `execution_failure`로 집계한다. 완료 실행만 자동 인용 일치·보류 적절성 분모에 포함하고, 리포트에는 전체 질의 수·완료 실행 수·실패 수·검토 대상 수를 함께 표시한다.

모델이 `grounded_demo`를 반환한 경우는 실행은 완료됐으나 생성 검증 실패 후 안전 발췌로 전환된 상태로 분리한다. 이를 `grounded` 성공이나 인프라 실패로 처리하지 않는다.

### 5. 실제 평가 실행은 명시적 CLI 모드와 결정론적 테스트 더블로 제공한다

`run_evaluation`에 실제 생성 결과를 별도 산출물로 생성하는 명시적 옵션을 추가한다. 테스트에서는 네트워크 없이 예측 가능한 답변자 더블을 주입해 산출물 구조·분모·실패 분리를 검증한다. 실제 Ollama 평가는 Docker Compose 또는 `OLLAMA_URL`이 설정된 환경에서만 실행한다.

대안으로 일반 평가 실행 때마다 Ollama를 자동 호출하는 방식은 CPU 실행 시간, 모델 다운로드 상태, 결과 변동성을 감추므로 채택하지 않는다.

## Risks / Trade-offs

- [CPU에서 72문항 생성이 오래 걸리거나 시간 초과한다] → CLI가 질의 ID·제한 수를 지원하고, 중단된 실행도 실패 레코드와 체크포인트로 남긴다.
- [인용 ID 일치만으로 문장 의미가 완전히 검증되지 않는다] → 자동 지표의 이름을 ‘인용 정답 근거 일치’로 제한하고, 생성문·근거·검토 필요 표시를 함께 제공한다.
- [모델 업데이트로 결과가 달라진다] → 모델명·프롬프트 해시·실행 시각·코퍼스 해시를 기록하며 이전 결과를 덮어쓰지 않는다.
- [실행 산출물에 과도한 원문이 저장된다] → 질문·생성문·청크 ID·기존 원문 URL만 기록하고, 코퍼스 본문과 API 키는 기록하지 않는다.

## Migration Plan

1. 기존 결정론적 평가 산출물과 리포트를 그대로 보존한다.
2. 실제 생성 평가 CLI와 별도 JSON·Markdown 리포트를 추가한다.
3. 네트워크 없는 테스트 더블로 새 산출물 계약을 검증한다.
4. Docker/Ollama에서 대표 실행을 수행하고, 결과의 실패 수와 검토 한계를 문서화한다.
5. 문제 발생 시 새 live 산출물·CLI만 비활성화하거나 삭제해 기존 검색·답변 경로로 되돌린다.

## Open Questions

- 실제 생성문 의미에 대한 사람 검토는 첫 실행에서 전체 72문항이 아니라 인용 불일치·`grounded_demo`·문서 비교 질의를 우선 표본으로 확인한다. 표본 수는 실행 결과의 실패율을 본 뒤 정하며, 자동 지표의 의미나 구현 작업은 바꾸지 않는다.
