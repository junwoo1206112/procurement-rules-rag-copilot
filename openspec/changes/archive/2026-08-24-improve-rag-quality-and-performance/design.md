## Context

현재 기본 경로는 `lexical_hybrid` 검색 결과의 상위 청크 전체를 로컬 Ollama에 전달하고, 모델이 반환한 claim과 citation ID를 검증한다. 이 방식은 인용 위조를 막지만, 서로 관련도 차이가 큰 후보가 함께 들어오면 모델이 빈 claim을 반환하여 `grounded_demo` 원문 발췌로 전환될 수 있다. 검색 평가는 고정 v3 세트와 코퍼스 해시 검증을 이미 사용하지만, 생성 답변 상태의 비율은 별도 지표로 수집하지 않으며 평가 리포트의 버전·수치가 실행 결과와 불일치할 위험이 있다. 동기는 [proposal.md](proposal.md)를 따른다.

## Goals / Non-Goals

**Goals:**

- 질문의 문서명·조항·핵심 어휘와 직접 연결된 청크를 생성 문맥에서 우선해, 검증 가능한 `grounded` 답변의 기회를 높인다.
- 검색 품질과 답변 상태를 같은 버전의 평가 세트·코퍼스·실행 조건에서 측정하고, 기본 경로 채택 여부를 증거로 결정한다.
- CPU 및 로컬 Ollama 환경에서 기존의 인용 검증·근거 부족 보류·원문 발췌 안전장치를 보존한다.

**Non-Goals:**

- 법률 해석의 정확성 보장, 외부 상용 LLM 도입, 실시간 코퍼스 수집, GPU 전용 최적화는 포함하지 않는다.
- 단일 평가 실행에서 더 높은 수치가 나왔다는 이유만으로 검색 기본값이나 포트폴리오 문구를 자동 변경하지 않는다.
- 생성 모델의 문장을 정답으로 간주하거나, 검증 실패 문장을 사용자에게 노출하지 않는다.

## Decisions

### 1. 생성 전용 근거 선택기를 검색기와 분리한다

`HybridRetriever.search()`는 사용자가 보는 검색 결과와 평가용 순위를 기존처럼 반환한다. 답변 단계에는 별도 `select_answer_evidence(question, hits)`를 두어 상위 후보를 생성 문맥용으로 재정렬·축소한다. 선택 점수는 다음 순서로 계산한다.

1. 질문의 공고번호, 문서명 또는 조항 표기가 청크 메타데이터와 직접 일치하는지
2. 질문 핵심 어휘가 청크 본문에 일치하는 비율과 BM25 양수 여부
3. 기존 hybrid 점수

단일 사실 질문은 직접 일치가 확인된 최상위 청크를 우선 전달한다. 질문에 둘 이상의 문서명·공고번호가 명시되거나 `비교`, `차이`, `각각` 같은 비교 의도가 있으면 각 명시 문서에서 가장 관련 높은 청크를 하나씩 유지한다. 직접 어휘 근거가 전혀 없으면 Ollama를 호출하지 않고 `insufficient_evidence`를 반환한다.

**대안:** 항상 `top_k=1`로 축소하는 방법은 간단하지만 문서 비교·복수 조건 질문의 필요한 근거를 제거한다. 검색 점수만 그대로 사용하는 방법은 현재의 혼합 후보 문제를 해결하지 못한다. 따라서 검색 순위 계약은 유지하고 생성 문맥만 목적에 맞게 선택한다.

### 2. API 상태명은 유지하고, 내부 원인과 평가 집계를 명시한다

기존 응답의 `grounded`, `grounded_demo`, `insufficient_evidence` 상태명은 호환성을 위해 유지한다. `grounded`는 claim·인용·최소 어휘 근거 검증을 모두 통과한 경우, `grounded_demo`는 모델 호출 또는 claim 검증 실패 뒤 검증된 발췌만 제공한 경우, `insufficient_evidence`는 생성 전에 관련 근거가 없어 호출하지 않은 경우다.

응답에 임의의 오류 전문을 노출하지 않고, 평가·로그에서는 상태별 건수와 제한된 원인 코드(`no_evidence`, `claim_validation_failed`, `model_unavailable`)를 집계한다. 원인 코드는 관찰·디버깅과 리포트용이며 모델의 미검증 텍스트를 정당화하는 근거가 아니다.

**대안:** 새로운 상태명을 추가하면 의미는 세분화되지만 기존 UI·API 소비자의 처리 분기가 늘어난다. 현재 상태는 사용자에게 필요한 안전 경계를 이미 표현하므로, 내부 원인 코드와 보고서로 관찰 가능성을 보완한다.

### 3. 생성 품질 평가는 결정론적 검증과 선택적 실제 모델 검증을 분리한다

고정 72문항 평가에는 모든 검색 구성별 Recall@k·MRR·nDCG·citation precision/recall·단건 p50/p95를 계속 산출한다. 여기에 질문별 선택 근거가 정답 청크와 겹치는지, 답변 상태가 무엇인지, 상태별 건수·비율을 추가한다. 네트워크·모델 속도에 좌우되지 않는 자동 회귀 테스트는 모의 Ollama 응답으로 세 상태와 인용 검증을 확인한다.

로컬 Ollama가 준비된 환경에서는 소규모 대표 질의의 실제 E2E 결과를 별도 기록한다. 이 결과는 컨테이너·모델 준비 상태를 함께 기록하며, 고정 단위 테스트의 대체물이 아니다.

**대안:** 72문항 전체를 실제 생성 모델로 매번 평가하면 더 직접적인 신호를 얻지만 CPU 데모의 시간이 길고 모델·하드웨어 차이로 재현성이 낮다. 따라서 자동 기준은 결정론적으로 유지하고, 실제 생성 결과는 투명한 보조 증거로 제한한다.

### 4. 기본 검색 구성은 비교 결과가 명확할 때만 변경한다

평가 실행은 현재 기본 `lexical_hybrid`와 실제 `embedding`, `hybrid`, `hybrid_rerank` 등 비교 가능한 구성에서 같은 코퍼스·같은 질의·같은 `top_k`를 사용한다. 후보가 기본값보다 Recall@5 또는 citation recall을 낮추거나 p95가 비현실적으로 높다면 기본값으로 채택하지 않는다. 리포트에는 선택하지 않은 구성의 낮아진 수치와 대표 실패 사례를 남긴다.

**대안:** Dense 단독의 현재 우세만으로 기본값을 바꾸면 최초 모델 다운로드·임베딩 캐시 준비 비용과 CPU 메모리 제약을 숨길 수 있다. 포트폴리오 데모는 즉시 재현 가능한 `lexical_hybrid`를 유지하고, 전환은 같은 조건의 개선 증거가 있을 때만 검토한다.

### 5. 평가 리포트는 실행 산출물에서 재생성하고 교차 대조한다

`data/evaluation-results.json`을 평가의 기계 판독 가능한 단일 결과로 두고, `docs/evaluation-report.md`와 README의 수치는 이 결과의 데이터셋 버전·코퍼스 해시·측정 버전과 대조한다. 작업 완료 조건은 리포트의 질문 수, 구성별 수치, 기본값 결정 및 실패 사례가 결과 JSON과 일치하는 것이다.

**대안:** 문서를 수동 갱신하면 설명은 빨라지지만 현재처럼 이전 실행 수치가 남을 수 있다. 리포트 생성 함수를 두어 결과와 문서를 함께 갱신하고, 테스트로 핵심 필드를 확인한다.

### 전문가 교차 검증 기록

**전문가 A:** 후보를 생성 전에 선택하지 않으면 claim 검증 실패가 검색 품질 문제인지 모델 문맥 혼선인지 분리할 수 없다. 직접 일치·본문 어휘·기존 점수를 분리한 선택기는 원인을 추적하면서도 기존 검색 API를 깨지 않는다.

**전문가 B:** `grounded` 비율만 올리려다 근거 부족 질문까지 생성시키면 포트폴리오의 안전성 주장이 무너진다. 답변 불가 질의의 보류율, `grounded_demo`의 발췌 인용 정합성, 낮은 구성의 실패 사례를 동일 리포트에 남겨야 한다.

**결정:** 직접 근거 선택과 상태별 측정을 함께 도입하되, 선택기가 근거를 찾지 못하면 생성하지 않으며 비교 질문의 복수 문서 근거는 보존한다. 이 결정은 템플릿의 품질·실패·재현성 축을 충족하는 구현 작업과 테스트로 전환한다.

## Risks / Trade-offs

- [선택기가 정답의 두 번째 근거를 제거할 수 있음] → 비교 의도·명시 문서 단위로 최소 한 청크를 보존하고, 복수 근거 평가 질의로 회귀 테스트한다.
- [한국어 조사·복합어 때문에 직접 일치 판정이 과도하게 보수적일 수 있음] → 기존 부분 문자열 어휘 일치를 재사용하고, 미일치는 안전한 보류로 처리하며 실패 사례를 리포트에 기록한다.
- [실제 모델은 빈 claim 또는 비정상 JSON을 반환할 수 있음] → JSON 형식 요청·claim 검증을 유지하고, 실패 시 검증된 발췌만 반환한다.
- [임베딩 첫 실행과 캐시 상태가 성능 수치를 왜곡할 수 있음] → 단건 측정 조건과 캐시 상태를 결과에 기록하고, 기본값 판단에는 동일 조건의 비교만 사용한다.
- [문서 리포트가 다시 실행 결과와 어긋날 수 있음] → 결과 JSON 기반의 리포트 생성 및 일치 테스트를 추가한다.

## Migration Plan

1. 선택기와 상태 원인 집계를 답변 경로에 추가하고, 기존 API 상태·인용 구조를 보존하는 단위·통합 테스트를 작성한다.
2. 평가 스키마와 리포트 생성기를 확장한 뒤 고정 데이터에서 모든 검색 구성을 재실행한다.
3. 결과 JSON, 평가 리포트, README, 전문가 인터뷰 기록의 수치를 교차 대조한다.
4. Docker Compose 환경에서 대표 직접 조항 질의와 근거 부족 질의를 재검증한다. 문제가 생기면 선택기 사용을 환경 변수로 끄거나 기존 상위 검색 결과 경로로 되돌리고, 검증되지 않은 생성 답변은 항상 차단한다.
